# smtp 587, 465

## smtp 587, 465

- 두 포트 모두 클라이언트가 인증 후 메일서버에 메일을 넘기는 용도(submission)
- TLS 를 언제 시작하는가의 차이

## 587 STARTTLS

- was -> 메일서버 tcp 연결
    - 587 또는 2587
- tcp 연결 이후 초기 smtp 메세지는 tcp 연결 위에서 smtp 로 평문 주고 받음
    - 서버측에서 STARTTLS 지원여부를 응답하고, 클라이언트가 STARTTLS 를 보내고 하는 등의 smtp 가 평문으로 오간 뒤 STARTTLS, TLS handshake 이후 암호화
- 중간에 평문으로 서버측에서 먼저 TLS 전환 지원여부를 응답하고, 클라이언트가 STARTTLS 를 보낸 뒤 서버가 수락하면 TLS handshake 시작
- 이후 암호화 smtp 통신

## 465 ImplictTLS

- was -> 메일서버 tcp 연결 이후 즉시 TLS handshake
    - SES 는 이 방식을 TLS Wrappe 라고 명칭
    - 465 또는 2465 포트 사용
- stmp 메세지가 평문으로 나가지 않음

## 587, 465보안상 차이

- 587의 경우 STARTTLS 통해 TLS handshake 진행 후 TLS 연결 수립하기 이전까지 평문 통신이므로 평문 구간에 개입할 여지가 생김
    - 공격 예시, STARTTLS 제거하여 서버가 TLS 지원하지 않는 것으로 클라이언트가 판단하고 SMTP 자격 증명을 평문으로 보냄
- 단, 클라이언트/서버 간 메일 제출 전에 TLS handshake 을 필수로 하는 것이 일반적이므로 이 구현을 따른다면 587, 465 보안상 유의미한 차이는 없음
- aws ses 사용시 모든 SMTP 연결에 TLS 를 요구하므로, 서버 측에서 평문으로 던지는 인증을 받아주는 케이스 없음
- 단, was 측에서 587(STARTTLS) 사용시 STARTTLS 사용 가능하면 사용으로 해두면 공격으로 중간 경로에서 STARTTLS가 제거도는 경우 was 가 평문으로 자격증명을 보낼 수 있음 (ses 가 아닌 공격자에게)
- 위와 같은 위험이 있을 수 있으므로 465를 1순위로 설정하고, 587 사용 필요한 경우 클라이언트 측에서 starttls 실패한 경우 평문 진행 여부 등 설정을 통해 보안위험 최소화 검토 필요

## 결론

- 465 를 우선적으로 검토하고, 어떤 이유로든 사용불가능 한 경우 587 사용
- 단, 587 사용시 starttls 실패한 경우 평문으로 자격증명 등이 보내지지 않도록 starttls.required=true 설정 권장
    - springboot 기준 spring.mail.properties.mail.smtp.starttls.required: true 설정 필요 (default: false)
- 587 사용하는 경우 굳이 465로 바꿀 필요는 없어보임.
